## 为什么叫 Spotlight？

大多数工作流告诉你"把所有事情都拆解清楚再动手"。Spotlight 不这么干。

**探照灯照到哪里，哪里才亮。** 拿到一个任务，先从总体目标反推需要哪些模块——但只深入拆解用户当前关注的模块。没提到的地方保持粗粒度，不提前过度拆解。

这不是偷懒。这是尊重注意力——在用户看到初版之前，你不知道哪些细节真正重要。与其猜，不如先做出来，让用户用"眼光"告诉你下一步往哪走。

```
用户眼光（探照灯）
      │
      ▼
┌──────────────┐
│  只拆这里     │  ← 用户关注的模块，逐层拆到底
└──────────────┘
      │
      ▼
┌──────────────┐
│  粗粒度跳过   │  ← 用户没问的模块，保持概要
└──────────────┘
```

## 命令体系

**你只需要记住一个命令：`/spotlight`。** 系统自动判断你的意图并路由到对应流程。

| 你说 | 系统自动 |
|------|---------|
| `/spotlight 帮我写实验报告` | 执行任务（先过快速通道判断，决定走全流程还是直接执行） |
| `/spotlight 初始化` | 引导安装 learn + claudework |
| `/spotlight 检查状态` | 输出安装诊断报告 |
| `/spotlight 切换写作风格` | 翻转混合模式 ↔ 纯学习模式 |
| `/spotlight` （无内容） | 检查状态，提示下一步 |

子命令（`/spotlight-init`、`/spotlight-work` 等）仍然存在，但不必记。

## 思维方式

### 不是"自底向上堆细节"，是"从总体反推"

传统思路：罗列所有需要的组件 → 逐个细化 → 组装。Spotlight 反过来：先看整体目标是什么 → 反推需要哪些大模块 → 用户眼光照到哪个模块就拆哪个。

```
用户说"做眼镜的手势识别"
        │
        ▼
  从总体目标反推
  ├── 硬件层（摄像头 + 计算模块）
  ├── 算法层（手势识别模型）
  └── 系统层（采集 → 推理 → 输出）
        │
        ▼
  用户追问"轻量化模型有哪些？"
        │
        ▼
  只拆算法层 → MobileNet / ShuffleNet / ...
  硬件层和系统层保持粗粒度
```

### 拆完必列 TODO，默认 3 条

任何任务分析完后，浓缩为 TODO 列表。大部分情况 3 条足够——按任务类型有对应的模板：

| 任务类型 | TODO 结构 |
|---------|----------|
| Bug 排查 | ①定位问题 ②分析链路 ③修复+验证 |
| 功能开发 | ①理清需求边界 ②设计实现路径 ③确定验收标准 |
| 调研选型 | ①明确调研目标 ②收集对比方案 ③输出结论建议 |
| 文档写作 | ①确定结构范围 ②填充核心内容 ③检查精简 |
| 代码审查 | ①明确审查维度 ②逐项检查记录 ③汇总优先级 |

**复杂任务不硬凑 3 条。** 多子系统、并行工作流、需要额外验证阶段——可以坦诚列 4 条或更多。核心原则：每条 TODO 要有独立存在的理由，不为凑数而拆分，不为省事而合并。

### 复杂 TODO 内部三层拆

```
主干（TODO）
  └── 分支（子步骤）
        └── 叶子（具体操作）
```

## 写作风格系统

这是 Spotlight 最有特色的部分之一。写作和表达是高度个人化的——别人的"好"不一定是你的"好"。

### 双模式设计

| 模式 | 风格来源 | 适用场景 |
|------|---------|---------|
| **混合模式**（默认） | Spotlight 内置规则 50% + 你个人风格 50% | 日常使用，有框架但不死板 |
| **纯学习模式** | 你的个人风格 100% | 你已经在 learn 里积累了足够的风格样本 |

`/spotlight-style` 一键切换。

### 内置六项铁律

1. **不用括号包参数** — `Adam，学习率 0.0008` 而非 `Adam(lr=0.0008)`
2. **步骤不写回顾** — 步骤写完就停，不写心得和感悟
3. **结果只写一段** — 汇总结论，不逐场景展开
4. **不用「一句话」引导语** — 「一句话说明」「一句话结论」这类前缀直接删掉，要总结就直接总结
5. **不用「说人话就是」类话术** — 读者本来就是人，这种前缀既多余，又暗示前半段不是人话
6. **「不是A而是B」改正面陈述** — 先给出结论 B，再补一句相对 A 好在哪

### 五维风格框架

分析任何参考文本时从五个维度入手：整体结构 → 段落模式 → 语言特征 → 与标准文体的差异 → 整体概括。

## 避坑清单：错误变成知识

这不是"注意事项列表"。这里的每一条都来自真实翻车现场——症状、原因、修复方法，三个不缺。

| 坑 | 翻车现场 | 正确做法 |
|----|---------|---------|
| officecli batch JSON 中文引号 | 解析报错 `'C' is invalid after a value` | 中文引用全部用方括号替代 |
| 用位置索引寻址段落 | 增删段落后其他元素偏移 | 用 stable paraId |
| 中英混合文件用 Edit | old_string 匹配失败 | 用 Write 全量覆写 |
| Windows 下用 `python3` | exit code 49 | 永远用 `python` |
| 逐段 set 效率低 | 中间出错难定位 | 构造 batch JSON 一次性提交 |
| 没确认图片位置就编辑 | 误删含图片段落 | 编辑前必跑 `officecli query image` |
| sed 低→高替换 | 连锁覆盖，结果跳级 | 从高数值往低数值替换 |
| useMemo 里做副作用 | shader uniform 不更新 | 用 useEffect 处理副作用 |

完整清单见 [SKILL.md §四](./SKILL.md)。

## 复盘机制：不重复交学费

每次项目完成（或犯了一个值得记住的错误），写入结构化复盘。为防止臃肿：

- **每条教训 ≤ 50 字**：够说清症状→修复即可
- **超过 20 条自动压缩**：合并为 5 条核心原则
- **下次任务只读近 3 篇摘要**：不加载全库，不挤压上下文

```
learn/
├── YYYY年-MM月-DD日-项目名称.md    ← 结构化复盘
├── YYYY年-MM月-DD日-项目名称.md    ← 超过 20 条已自动压缩
├── ...
└── archive/                       ← 超过 30 个文件时旧文件归档
```

同一个坑不掉两次，复盘库也不会变成臃肿黑洞。

## 技能联动

Spotlight 会在任务中自动检测并调用已安装的关联技能：

| 场景 | 联动技能 |
|------|---------|
| Word 文档读写 | `officecli` |
| PPT 制作 | `ppt-master` |
| 论文写作/润色 | `nature-writing`、`nature-polishing` |
| 代码审查 | `code-review` |
| 项目初始化 | `init` |

任务结束后，如果发现本次涉及但未安装的技能，会自动给出推荐。
